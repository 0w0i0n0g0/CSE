## 04. Kubernetes

### 0. 이전 시간 복습 및 질의응답 (Q&A)

쿠버네티스를 이해하기 위한 핵심 기반 지식입니다.

- **VM(가상머신)과 컨테이너(Docker)의 차이점**
  - **VM:** 하드웨어(인프라) 위에 하이퍼바이저(Hypervisor)를 깔고, 그 위에 각각 독립된 게스트 OS를 설치한 뒤 애플리케이션이 구동되는 방식입니다.
  - **Docker(컨테이너):** 하드웨어 위에 호스트 OS를 깔고, 그 위의 도커 엔진 레벨에서 애플리케이션(컨테이너)이 구동됩니다. 즉, **OS를 공유하느냐(도커) 아니냐(VM)** 의 레벨 차이가 가장 큽니다.
- **컨테이너의 격리 및 보안 문제 (핵심)**
  - 도커는 호스트 OS를 공유하므로 한 컨테이너에 문제가 생기면 다른 컨테이너나 호스트 OS에 영향을 줄 수 있습니다. (간섭 현상 및 장애 전파)
  - 이를 해결하기 위해 리눅스 커널의 **cgroups** (성능 및 자원 할당 제한)와 **namespace** (영역 분리)를 사용하여 격리성을 확보합니다. (예: CPU, 메모리 쿼터/리미트 설정)
  - 보안 측면에서는 여전히 VM이 더 안전합니다. 도커는 보안을 위해 Rootless Docker, 샌드박싱, 전용 보안 런타임, 지속적인 스캐닝 등 추가적인 보안 솔루션이 필수적입니다.
- **보안 취약점에도 불구하고 도커를 사용하는 이유**
  - 비용 절감, 거대한 생태계(Ecosystem), 편의성, 오버헤드 감소, 빠른 배포 속도 등 기회비용 측면에서 압도적인 장점이 있기 때문입니다.
  - 최근 클라우드 데이터 센터는 성능이 좋아져 관리가 편한 컨테이너 기반으로 모두 전환(Migration)되는 추세입니다.

### 1. 쿠버네티스 소개 및 어원

- **쿠버네티스(Kubernetes)**: 구글(Google)의 내부 시스템이었던 Borg와 Omega를 개발하고 운영하며 얻은 경험과 교훈을 바탕으로 스핀아웃(spin out)된 **오픈소스 컨테이너 오케스트레이션 플랫폼** 입니다.
- **어원**: 그리스어로 **"조타수(pilot)"** 또는 **"배의 키잡이(Helmsman of a ship)"** 를 의미합니다.
  - 도커의 로고가 컨테이너를 싣고 있는 고래라면, 쿠버네티스는 그 배가 어디로 갈지 방향을 결정하고 컨테이너들을 지휘하는 키잡이 역할을 한다는 의미입니다.
- **목적**: 워크로드의 **배포(deploying), 유지보수(maintaining), 확장(scaling)** 을 중심으로 설계된 느슨하게 결합된(loosely coupled) 컴포넌트들의 집합입니다.

### 2. 컨테이너 오케스트레이션 (Container Orchestration)

- **오케스트레이션(Orchestration) vs 코레오그래피(Choreography)**
  - **오케스트레이션:** 오케스트라의 지휘자처럼 중앙의 컨트롤러(마스터)가 존재하여 매니지드 노드들에게 일을 지시하고 작업의 순서(워크플로우)를 관리하는 중앙 집중형 방식입니다. (쿠버네티스가 채택한 방식)
  - **코레오그래피:** 중앙 지휘자 없이 노드들끼리 서로 분산 통신하며 이벤트를 기반으로 알아서 협업하는 방식입니다.
- **도커의 동적 관리 문제**
  - 컨테이너 플랫폼으로서의 도커는 마이크로서비스 아키텍처(Microservices architecture)를 기반으로 애플리케이션을 패키징하는 데 매우 인기 있습니다.
  - 수요에 따라 컨테이너 숫자가 동적으로 폭증할 때, 수많은 컨테이너의 수명 주기(lifecycle)를 관리하는 것은 극도로 어려워집니다.
  - 구글이나 아마존처럼 거대한 데이터 센터에서 수만 대의 컨테이너를 사람이 수동으로 배치하고 관리하는 것은 불가능합니다.
- **컨테이너 오케스트레이션의 역할**
  - 컨테이너의 **스케줄링, 배포, 확장성, 로드 밸런싱, 가용성, 네트워킹을 '자동화(automating)'** 하여 문제를 해결합니다.
  - 컨테이너와 서비스의 수명 주기를 자동화하고 관리하는 것입니다.
- **주요 오케스트레이션 도구**
  - Kubernetes, OpenShift, Nomad, Docker Swarm, Docker Compose, MiniKube, Marathon, Cloudify, Rancher, Containership, AZK, GKE, AKS, AWS EKS 등이 있습니다.
  - 과거에는 Docker Swarm과 경쟁했으나 현재는 쿠버네티스가 천하통일했습니다.
  - GKE(Google), EKS(AWS), AKS(Azure)는 클라우드 벤더사들이 제공하는 매니지드 쿠버네티스 서비스입니다.

### 3. 쿠버네티스의 특징 및 기능

- **개요**
  - 구글이 설계하고 현재 **CNCF(Cloud Native Computing Foundation)** 에서 유지 관리하는 오픈소스 플랫폼입니다.
  - **선언적 구성(Declarative Configuration)** 과 **자동화(automation)** 를 모두 지원합니다.
  - 컨테이너화된 워크로드 및 서비스의 배포, 확장, 관리를 자동화합니다.
- **명시적 선언의 중요성 (Desired State)**
  - "1번, 2번, 3번 순서대로 해라"라고 명령하는 것이 아니라, "나는 항상 4개의 인스턴스가 띄워져 있는 상태(Desired State)를 원해"라고 선언(문서화)만 하면 쿠버네티스가 알아서 그 상태를 유지해 주는 핵심 개념입니다.
- **분산 시스템의 리눅스 커널**
  - 분산 시스템의 **리눅스 커널(Linux kernel)** 로 알려져 있습니다.
  - 노드의 **기본 하드웨어를 추상화(Abstracts away)** 하여, 워크로드가 배포되고 공유 리소스 풀을 소비할 수 있는 **단일화된 인터페이스(uniform interface)** 를 제공합니다.
  - 시스템의 **실제 상태(actual state)** 와 **원하는 상태(desired state)** 를 일치(converging)시켜 상태를 해결하는 **엔진(engine)** 역할을 합니다.
  - 분산된 여러 대의 컴퓨터를 마치 하나의 거대한 컴퓨터처럼 사용할 수 있게 해주는 OS 역할을 합니다.
- **주요 기능**
  - 모든 서비스는 기본적으로 **로드 밸런싱(Load Balancing)** 이 지원됩니다.
  - 동적으로 스케일 업 및 스케일 다운이 가능합니다.
  - 애플리케이션의 **자가 치유(Self-Healing)** 및 원활한 **업그레이드 또는 롤백(rollback)** 을 활성화하는 데 사용됩니다.
  - **워크로드 자동 확장 (Autoscale Workloads)**
  - **Blue/Green Deployments:** 무중단 배포 (Blue: 이전 버전, Green: 새 버전)
  - 작업 및 예약된 크론잡 실행 (Fire off jobs and cronjobs)
  - Stateless 및 Stateful 애플리케이션 관리
  - 서비스 디스커버리의 기본 메서드 제공
  - 서드파티 앱의 손쉬운 통합 및 지원
- **클라우드 벤더 독립성**
  - **동일한 API(SAME API)** 를 베어메탈(bare metal)과 **모든 클라우드 제공업체(EVERY cloud provider)** 에서 똑같이 사용할 수 있습니다!
  - 온프레미스 서버를 쓰든, AWS, GCP, Azure를 쓰든 동일한 쿠버네티스 API로 관리할 수 있어 특정 벤더에 종속되지 않는다는 강력한 장점이 있습니다.

### 5. 핵심 개념: 파드(Pod)와 서비스(Service)

#### 5.1 파드 (Pod)

- **원자적 단위(Atomic unit)**: 쿠버네티스의 가장 작은 "작업 단위(unit of work)"입니다.
- 파드는 볼륨과 네트워크 네임스페이스를 공유하고 단일 컨텍스트의 일부인 **하나 이상의 컨테이너(one or MORE containers)** 모음입니다. (단일 컨테이너가 아닐 수도 있습니다.)
- **일시적(Ephemeral!)**: 파드는 언제든 죽고 새로 생성될 수 있는 일시적인 존재입니다.
- 파드는 IP를 공유합니다. 쿠버네티스는 컨테이너 하나만 배포할 수 없고, 반드시 파드라는 단위로 감싸서 배포해야 합니다. 파드가 죽으면 IP도 변경됩니다.

#### 5.2 서비스 (Service)

- 파드의 노출된 워크로드에 접근하는 **통합된 방법(Unified method)**.
- **영속적 리소스(Durable resource / NOT Ephemeral!)**: 파드는 일시적이지만 서비스는 고정적입니다. 고정(static) 클러스터 IP와 네임스페이스 기반의 고정 DNS 이름을 제공합니다.
- 쿠버네티스에서 서비스는 파드의 논리적 집합과 접근 정책을 정의하는 추상화입니다. 파드가 생성, 파괴, 이동하더라도 안정적인 네트워크 엔드포인트를 제공하여 지속적인 연결을 보장합니다.
- 파드가 죽어서 IP가 계속 바뀌면 클라이언트가 접속할 수 없습니다. 따라서 앞에 절대 변하지 않는 IP를 가진 '서비스'를 두고, 서비스가 살아있는 파드들에게 트래픽을 로드밸런싱 해주는 구조입니다.

### 6. 쿠버네티스 아키텍처

- **전체 구조**
  - **Kubernetes Control Plane (마스터 노드)**: kube-controller-manager, cloud-controller-manager, kube-api-server, kube-scheduler, etcd
  - **Kubernetes Nodes (워커 노드)**: kubelet, kube-proxy, Container Runtime Engine
  - 사용자는 `kubectl`을 통해 마스터 노드의 `kube-apiserver`에 명령을 내립니다.

#### 6.1 컨트롤 플레인 컴포넌트 (Control Plane Components)

- **kube-apiserver**
  - 쿠버네티스 컨트롤 플레인과 데이터스토어(etcd)로 향하는 **전면 REST 인터페이스** 를 제공합니다.
  - 모든 클라이언트와 애플리케이션이 **엄격하게(strictly)** API 서버를 통해서만 쿠버네티스와 상호 작용합니다.
  - 데이터스토어의 프론트엔드 역할을 할 뿐만 아니라 인증/인가, 요청 검증, 변형(mutation), 어드미션 컨트롤을 처리하여 클러스터의 **게이트키퍼(gatekeeper)** 역할을 합니다.
- **etcd ([https://etcd.io/](https://etcd.io/))**
  - 클러스터 데이터스토어 역할을 합니다.
  - 쿠버네티스에서 클러스터 상태를 영구적으로 저장하기 위한 강력하고 일관되며 고가용성을 가진 **키-값 저장소(key-value store)** 입니다.
  - 객체 및 설정(config) 정보를 저장합니다.
  - **Raft Consensus 알고리즘 사용**: 클러스터의 내결함성을 갖춘 일관된 "뷰(view)"를 생성하기 위해 시스템 정족수(quorum) 간에 "Raft 합의" 알고리즘을 사용합니다.
  - 분산 시스템에서 마스터 노드가 죽었을 때 누가 리더가 될지 투표(Election)로 결정하는 알고리즘입니다.
  - **스플릿 브레인(Split-brain) 문제**: 노드를 짝수(예: 4대)로 두면, 네트워크 단절 시 2:2로 나뉘어 서로 자신이 리더라고 주장하는 문제가 생깁니다. 따라서 etcd 노드는 무조건 **홀수(3, 5, 7대)** 로 구성하여 과반수(Majority) 투표가 이루어지도록 설계해야 합니다.
- **kube-controller-manager**
  - 모든 핵심 컴포넌트 컨트롤 루프를 관리하는 **기본 데몬(primary daemon)** 역할.
  - API 서버를 통해 클러스터 상태를 지속적으로 **모니터링(Monitors)** 하고, 클러스터를 **원하는 상태(desired state)로 조향(steers)** 합니다.
- **kube-scheduler**
  - 워크로드 요구 사항을 평가하고 리소스에 일치시키려 시도하는 정책이 풍부한 엔진입니다.
  - 기본 스케줄러는 **빈 패킹(bin packing)** 알고리즘을 사용합니다.
  - **워크로드 요구 사항**: 일반 하드웨어 요구 사항, 어피니티/안티-어피니티(affinity/anti-affinity), 라벨(labels) 및 기타 맞춤형 리소스 요구 사항이 포함됩니다.
  - 기본 빈 패킹(바구니에 짐 채우기) 알고리즘 대신, 최근에는 딥러닝/강화학습(Reinforcement Learning)을 사용해 스케줄링을 최적화하는 연구가 활발합니다.
  - **SK 하이닉스 공장 사례:** 반도체 라인의 장비(서버)가 멈추면 막대한 손실이 발생합니다. 따라서 중요한 서비스의 복제본(Replica)들은 한 랙(Rack)이나 한 노드에 몰아서 배치하면 안 됩니다(전원 코드가 뽑히면 다 죽으므로). 이때 서로 다른 노드에 떨어뜨려 배치하도록 설정하는 것이 **안티-어피니티(anti-affinity)** 입니다.

#### 6.2 노드 컴포넌트 (Node Components)

- **kubelet**
  - 호스트의 모든 파드 수명 주기를 관리하는 **노드 에이전트(node agent)** 입니다.
  - kubelet은 YAML 컨테이너 매니페스트를 이해하며 여러 소스에서 읽어옵니다: 파일 경로, HTTP 엔드포인트, etcd 변경 사항 감시, 단순 API를 통한 HTTP 서버 모드.
  - 마스터 노드(API 서버)의 명령을 받아 실제 노드에서 컨테이너를 띄우고 상태를 보고하는 일꾼입니다.
- **kube-proxy**
  - 각 노드의 **네트워크 규칙(network rules)** 을 관리합니다.
  - 쿠버네티스 클러스터 서비스에 대한 **연결 전달(connection forwarding) 또는 로드 밸런싱** 을 수행합니다.
  - **사용 가능한 프록시 모드:** Userspace, iptables, ipvs (지원되는 경우 기본값).
  - 서비스(Service) 개념을 구현하여 트래픽을 실제 파드로 포워딩해 주는 역할을 합니다. 최근에는 Istio 등 Service Mesh 기술(Envoy Proxy)과 연계되어 더욱 고도화되고 있습니다.
- **Container Runtime Engine**
  - 컨테이너 런타임은 컨테이너를 실행하고 관리하는 **CRI(Container Runtime Interface)** 호환 애플리케이션입니다.
  - **종류:** Containerd (Docker), Cri-o, Rkt, Kata (이전의 clear 및 hyper), Virtlet (VM CRI 호환 런타임).

#### 6.3 옵셔널 서비스 및 클라우드 컨트롤러

- **cloud-controller-manager**
  - 클라우드 제공업체별 지식 및 통합 기능을 쿠버네티스 핵심 컨트롤 루프에 제공하는 데몬입니다. (예: AWS, GCP 등의 로드밸런서나 스토리지와 연동)
  - 노드, 라우트, 서비스 컨트롤러가 포함되며, PersistentVolume 라벨 같은 것들을 처리합니다.
- **Cluster DNS**
  - 쿠버네티스 서비스를 위한 클러스터 전역 DNS를 제공합니다.
  - **CoreDNS** 기반으로 구축되어 있습니다.
- **Kube Dashboard**
  - 쿠버네티스 클러스터를 위한 제한적이고 다목적인 웹 프론트 엔드(Web UI)입니다.
- **Heapster / Metrics API Server**
  - 다른 쿠버네티스 컴포넌트에서 사용할 수 있도록 **메트릭(metrics)** 을 제공합니다.
  - Heapster는 더 이상 사용되지 않으며(deprecated), 현재는 **Metrics API** 를 사용합니다.

### 7. 쿠버네티스 네트워킹

#### 7.1 네트워크 계층 구조

- **Pod Network**: CNI(Container Network Interface) 플러그인에 의해 관리되며, 파드 간 통신(pod-to-pod)에 사용되는 클러스터 전역 네트워크입니다.
- **Service Network**: kube-proxy에 의해 서비스 디스커버리용으로 관리되는 클러스터 전역의 **Virtual IPs(가상 IP)** 범위입니다.

#### 7.2 Container Network Interface (CNI)

- 쿠버네티스 내의 파드 네트워킹은 CNI를 통해 배관(plumbed)됩니다.
- 컨테이너 런타임과 네트워크 구현 플러그인 사이의 인터페이스 역할을 합니다.
- CNCF 프로젝트이며 간단한 JSON 스키마를 사용합니다.
- **CNI Plugins 목록:** Amazon ECS, Calico, Cillium, Contiv, Contrail, Flannel, GCE, kube-router, Multus, OpenVSwitch, Romana, Weave. (강의에서는 주로 Flannel, Calico 등이 언급됨)

#### 7.3 핵심 네트워킹 규칙 (Fundamental Networking Rules)

- 파드 내의 모든 컨테이너는 방해받지 않고(unimpeded) 서로 통신할 수 있습니다.
- 모든 파드는 NAT(Network Address Translation) 없이 모든 다른 파드와 통신할 수 있습니다.
- 모든 노드는 NAT 없이 모든 파드와 통신할 수 있습니다 (그 반대도 마찬가지).
- 파드가 스스로를 보는 IP는 다른 존재가 그 파드를 볼 때의 IP와 동일합니다.

#### 7.4 통신 패턴

- **Container-to-Container (컨테이너 간)**: 파드 내의 컨테이너는 **동일한 네트워크 네임스페이스** 에 존재하며 IP를 공유합니다. `localhost`를 통해 파드 내부 통신이 가능합니다.
- **Pod-to-Pod (파드 간)**: 수명 주기 동안 클러스터 **고유 IP** 가 할당됩니다. 파드 자체는 근본적으로 일시적(ephemeral)입니다.
- **Pod-to-Service (파드 대 서비스)**: kube-proxy에 의해 관리되며 영구적인 클러스터 고유 IP를 부여받습니다. 파드의 수명 주기를 넘어 존재합니다.
- **External-to-Service (외부 대 서비스)**: kube-proxy에 의해 처리되며, 클라우드 제공업체 또는 기타 외부 엔티티(로드 밸런서)와 협력하여 작동합니다.

### 8. Self-Healing (자가 치유) 메커니즘

- 쿠버네티스는 항상 클러스터를 **원하는 상태(desired state)** 로 이끌기 위해 노력합니다.
- **대화 예시:**
  - 나: "나는 항상 3개의 건강한 redis 인스턴스가 실행되길 원해."
  - 쿠버네티스: "알았어, 항상 3개의 인스턴스가 실행되도록 보장할게."
  - 쿠버네티스: "오 이런, 하나가 죽었네. 새로운 하나를 다시 띄워야겠다."

---

### 9. 최신 연구 동향 및 실제 사례

- **오픈소스 프로젝트 참여**
  - 오픈소스 프로젝트(깃허브)에 참여하고 PR(Pull Request)을 날리는 문화에 대한 이해가 중요합니다.
  - Linux Foundation, CNCF 등의 생태계 기여 방식을 알아두어야 합니다.
- **교수님 연구실 사례: UAM(도심항공교통) x 쿠버네티스**
  - 쿠버네티스의 노드(Node)는 일반적으로 고정된 컴퓨터지만, 교수님 연구실에서는 **UAM(도심항공교통, 드론/플라잉카)** 을 쿠버네티스의 워커 노드로 만드는 연구를 진행 중입니다.
  - 움직이는 모빌리티(자동차, 드론)에 쿠버네티스 에이전트를 올려 분산 시스템을 구축하고, PX4(오픈소스 비행 제어 소프트웨어)와 언리얼 엔진(Unreal Engine) 비행 시뮬레이터를 쿠버네티스와 결합하여 자율주행 및 보안 아키텍처를 시뮬레이션하는 연구를 수행하고 있습니다.
  - 이러한 최신 연구 트렌드와 오픈소스 생태계(Linux Foundation, CNCF)의 기여 방식에 대해 이해하는 것이 중요합니다.

### 📝 시험 예상 문제 및 해설

#### Q1. 쿠버네티스의 어원과 의미, 그리고 도커와의 관계를 설명하시오.

- **해설**:
  - **어원**: 그리스어로 **"조타수(pilot)"** 또는 **"배의 키잡이(Helmsman)"** 를 의미합니다.
  - **의미**: 도커(고래/컨테이너)가 화물을 싣고 있다면, 쿠버네티스는 그 배의 방향을 결정하고 컨테이너들을 지휘하는 키잡이 역할을 합니다.
  - **도커와의 관계**: 쿠버네티스는 도커 컨테이너의 배포, 확장, 관리를 자동화하는 **컨테이너 오케스트레이션 플랫폼** 입니다.

#### Q2. 쿠버네티스가 채택한 오케스트레이션(Orchestration)과 코레오그래피(Choreography)의 차이점을 설명하시오.

- **해설**:
  - **Orchestration (오케스트레이션)**: 중앙의 컨트롤러(마스터/지휘자)가 존재하여 매니지드 노드들에게 일을 지시하고 작업 순서를 관리하는 **중앙 집중형** 방식입니다. 쿠버네티스가 채택한 방식입니다.
  - **Choreography (코레오그래피)**: 중앙 지휘자 없이 노드들끼리 서로 분산 통신하며 이벤트를 기반으로 알아서 협업하는 **분산형** 방식입니다.

#### Q3. 쿠버네티스의 'Desired State(원하는 상태)' 선언적 구성 개념을 설명하시오.

- **해설**:
  - 사용자가 "항상 4개의 인스턴스가 실행되도록"이라고 **선언(문서화)** 만 하면, 쿠버네티스가 알아서 현재 상태(actual state)를 원하는 상태(desired state)와 일치(converging)시키도록 관리하는 방식입니다.
  - "어떻게(How)"가 아닌 **"무엇을(What)"** 원하는지 선언하면 시스템이 자동으로 조정합니다.

#### Q4. etcd에서 Raft Consensus 알고리즘을 사용하는 이유와, 왜 홀수(3, 5, 7대)로 구성해야 하는지 설명하시오.

- **해설**:
  - **Raft Consensus**: 분산 시스템에서 마스터 노드가 죽었을 때 누가 리더가 될지 **투표(Election)** 로 결정하는 알고리즘입니다.
  - **홀수 필요성**: 노드를 **짝수(예: 4대)** 로 두면 네트워크 단절 시 2:2로 나뉘어 서로 자신이 리더라고 주장하는 **스플릿 브레인(Split-brain)** 문제가 발생합니다. 따라서 **과반수(Majority)** 투표가 가능한 홀수로 구성해야 합니다.

#### Q5. 파드(Pod)와 서비스(Service)의 차이점과, 왜 두 개념이 모두 필요한지 설명하시오.

- **해설**:
  - **파드(Pod)**: 쿠버네티스의 가장 작은 작업 단위로, 하나 이상의 컨테이너 모음입니다. **일시적(Ephemeral)** 이며 언제든 죽고 새로 생성될 수 있어 IP가 변경됩니다.
  - **서비스(Service)**: 파드의 논리적 집합에 대한 고정된 접근점을 제공하는 **영속적 리소스** 입니다. 고정 IP와 DNS 이름을 가지며, 파드가 변경되어도 안정적인 네트워크 엔드포인트를 유지합니다.
  - **필요성**: 파드의 IP가 계속 바뀌면 클라이언트가 접속할 수 없으므로, 변하지 않는 서비스 IP를 통해 로드밸런싱되는 구조가 필요합니다.

#### Q6. 쿠버네티스 Control Plane의 4가지 핵심 컴포넌트와 각각의 역할을 기술하시오.

- **해설**:
  - **kube-apiserver**: 모든 클라이언트가 쿠버네티스와 상호작용하는 **유일한 입점(REST 인터페이스)** 이자 인증/인가의 **게이트키퍼** 역할.
  - **etcd**: 클러스터 상태를 영구 저장하는 **키-값 저장소** (Raft 합의 알고리즘 사용).
  - **kube-controller-manager**: 클러스터 상태를 모니터링하고 **원하는 상태로 조향** 하는 기본 데몬.
  - **kube-scheduler**: 워크로드 요구사항을 평가하여 적절한 노드에 파드를 배치하는 **스케줄러** (기본 빈 패킹 알고리즘 사용).

#### Q7. 쿠버네티스 워커 노드의 3가지 컴포넌트와 각각의 역할을 설명하시오.

- **해설**:
  - **kubelet**: 마스터(API 서버)의 명령을 받아 실제 노드에서 컨테이너를 띄우고 수명 주기를 관리하는 **노드 에이전트**.
  - **kube-proxy**: 서비스 개념을 구현하여 트래픽을 실제 파드로 **포워딩/로드밸런싱** 하는 네트워크 프록시.
  - **Container Runtime Engine**: CRI(Container Runtime Interface)를 통해 컨테이너를 실행하고 관리하는 런타임 (Containerd, Cri-o 등).

#### Q8. 쿠버네티스에서 '안티-어피니티(anti-affinity)'가 필요한 상황의 예시를 들고 그 이유를 설명하시오.

- **해설**:
  - **상황 예시**: SK 하이닉스 공장의 반도체 라인 장비(서버) - 한 대가 멈추면 막대한 손실 발생.
  - **이유**: 중요한 서비스의 복제본(Replica)들을 **한 랙이나 한 노드에 몰아서 배치** 하면, 전원 코드가 뽑히는 등의 상황에서 모든 복제본이 동시에 죽을 수 있습니다.
  - **안티-어피니티**: 서로 다른 노드에 떨어뜨려 배치하도록 설정하여 **장애 격리(Fault Isolation)** 를 확보합니다.

#### Q9. 쿠버네티스의 자가 치유(Self-Healing) 메커니즘을 예시와 함께 설명하시오.

- **해설**:
  - 사용자가 "항상 3개의 건강한 인스턴스를 원한다"고 선언(desired state)하면, 쿠버네티스는 이 상태를 지속적으로 모니터링합니다.
  - 만약 하나의 인스턴스가 죽어 현재 상태(actual state)가 2개가 되면, 쿠버네티스는 자동으로 새로운 인스턴스를 생성하여 원하는 상태(3개)로 복구합니다.

#### Q10. 쿠버네티스의 'Blue/Green Deployment'와 같은 무중단 배포 전략의 이점을 설명하시오.

- **해설**:
  - **Blue**: 현재 운영 중인 안정적인 이전 버전.
  - **Green**: 배포하려는 새 버전.
  - **이점**: Green 버전을 완전히 준비한 후 트래픽을 한 번에 전환하면, 롤백이 필요할 때 즉시 Blue로 되돌릴 수 있어 **서비스 중단 없이 안전한 배포** 가 가능합니다.
